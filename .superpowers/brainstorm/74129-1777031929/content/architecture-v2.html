小程序页面结构 & 核心流程

4 个 Tab 页面 + 核心记录流程

1. 小程序 Tab 页面结构
┌───────────────────────────────────────────────┐
│  TabBar                                                │
│  ┌──────────┬──────────┬──────────┬──────────┐ │
│  │ 今日记录 │  添加    │  日历    │  对话    │ │
│  │ (首页)   │  (+)     │  (历史)  │  (AI)   │ │
│  └──────────┴──────────┴──────────┴──────────┘ │
└───────────────────────────────────────────────┘

Tab 1 — 今日记录（首页）
  • 今日热量+营养素环形图
  • 已记录的食物列表
  • 默认展示"今天"

Tab 2 — 添加（核心入口）
  • 语音输入 或 文字输入
  • → 发送到后端解析 → 展示解析结果
  • → 用户确认/编辑 → 保存
  这是最主要的使用路径

Tab 3 — 日历
  • 日历组件选择日期
  • 展示选中日期的摄入汇总
  • 点击某天查看当天食物列表

Tab 4 — 对话
  • 独立的 LLM 聊天界面
  • 自然语言提问（如"我这周蛋白质够吗？"）
  • SSE 流式返回
2. 添加记录 — 核心数据流

小程序端                     FastAPI 后端

  用户输入文字/语音
       │
       ▼
  POST /api/records/parse  ────────►  1. 查食物数据库
  { "text": "一碗米饭和红烧肉" }              │
           │                       命中? ──Yes──► 返回数据库数据
           │                          │
           │                         No
           │                          │
           │                        2. LLM 估算
           │                       解析: 米饭150g=174kcal
           │                       红烧肉200g=490kcal
           │                          │
           │                   3. 写缓存+返回
           │                          │
       ◄──────────────────────────────┘
  返回解析结果列表:
  [
    { name:"米饭", kcal:174, protein:3.5, carbs:39, fat:0.5 },
    { name:"红烧肉", kcal:490, protein:15, carbs:8, fat:44 }
  ]
       │
       ▼
  用户确认页面
  • 可以修改任意字段
  • 可以删除某条
  • 可以追加食物
       │
       ▼
  POST /api/records  ──────────────► 存入 PostgreSQL
  { date, meals: [...] }

数据流要点

关键分离

  • 解析和保存是两个 API — parse 只做文本→食物映射，不写库；保存是独立的写库操作
  • 语音在小程序端完成 — 后端从来不知道音频长什么样
  • 对话走独立的对话 API — 和记录 CRUD 不耦合
