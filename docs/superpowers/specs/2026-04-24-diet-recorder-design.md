# 每日饮食记录 Agent — 设计文档

## 概述

一个基于 ReAct Agent 的每日饮食记录工具。用户通过微信小程序以语音或文字对话，Agent 自动解析食物、计算热量和宏量营养素，用户确认后保存。同时支持自然语言查询历史记录和营养咨询。

### 核心特征

- **纯对话交互**：无导航、无 TabBar，所有功能通过对话唤醒
- **ReAct Agent**：LangGraph 构建，Agent 自主推理-行动-观察循环
- **RAG 食物知识库**：向量检索食物营养数据，数据库优先 + LLM 兜底
- **多用户**：微信授权登录，用户数据隔离
- **语音 + 文字输入**：语音在小程序端完成识别，后端只收文本

```

│  │ Agent 开场白                    │  │
│  │ 你好！我是你的饮食助手...        │  │
│  └───────────────────────────────┘  │
│           ┌─────────────────────┐    │
│           │ 用户消息气泡          │    │
│           │ 中午吃了米饭红烧肉     │    │
│           └─────────────────────┘    │
│  ┌───────────────────────────────┐  │

├─────────────────────────────────────┤
│  🎤 │ 说点什么...               │ ➕ │
└─────────────────────────────────────┘
```

### 消息类型

1. **文本消息**：用户输入和 Agent 普通回复
2. **确认卡片**：食物解析结果，包含食物项、热量、营养素、确认/修改按钮
3. **日历卡片**：查看历史时，嵌入日期切换 + 摄入汇总 + 食物列表
4. **拒绝消息**：与饮食无关的话题，显示"抱歉，我只能帮你记录饮食和回答食物相关问题"

### 输入方式

- **文字输入**：底部输入栏直接打字
- **语音输入**：点击 🎤 触发微信同声传译插件，识别结果填入输入栏
- **语音模块可替换**：通过统一接口封装，后续可切换为后端 ASR

### 数据缓存

- 使用 `wx.setStorageSync` 缓存最近 7 天的摄入汇总，日历页减少请求
- 聊天消息本地缓存（最近 50 条），避免每次打开页面空白

## 后端设计

### API

| 端点 | 方法 | 说明 |
|------|------|------|
| `/api/auth/login` | POST | 微信登录，接收 `code` 换取 `openid`，返回 JWT |
| `/api/chat` | POST | 对话接口，SSE 流式返回 Agent 响应 |

### 微信登录流程

`wx.login()` 为静默调用，无需用户授权，登录对用户完全无感。

```
小程序打开
    │
    ▼
wx.login() → 拿到临时 code（静默，无弹窗）
    │
    ▼
POST /api/auth/login { code }
    │
    ▼
后端 code → 微信接口换 openid
    │
    ▼
查数据库：新用户→自动注册 / 老用户→识别身份
    │
    ▼
签发 JWT，返回 token
    │
    ▼
小程序存 token → 后续请求 Header: Authorization: Bearer <token>
```

- **首次用户**：打开即登录，Agent 弹出开场白「你好！我是你的饮食助手...」
- **老用户**：打开即登录，Agent 跳过开场白，直接问候并带出今日摄入数据
- **Token 过期**：返回 401 → 小程序自动重新 `wx.login()` 续期，用户无感
- **无需头像/昵称**：纯对话场景无展示需求，openid 即用户凭证

### LangGraph ReAct Agent

#### 图结构

```
START → agent_node (LLM 推理 + 工具选择)
          ↙         ↘
    有工具调用      无工具调用（直接回复）
       ↓                ↓
   tool_node         END
   (执行工具)
       ↓
   agent_node
   (观察结果，继续推理)
```

#### 工具定义

| 工具名 | 功能 | 输入 | 输出 |
|--------|------|------|------|
| `search_food` | RAG 检索食物营养数据 | 食物名称字符串 | 匹配食物列表（名称、热量、三大营养素/100g、置信度） |
| `save_record` | 保存确认后的饮食记录 | 用户 ID、日期、餐次、食物列表 | 保存成功/失败 |
| `get_daily_summary` | 查询某日摄入汇总 | 用户 ID、日期 | 总热量、三大营养素合计、食物列表 |
| `query_history` | 查询日期范围的记录 | 用户 ID、起止日期 | 每日汇总列表 |
| `refuse` | 拒绝无关话题 | — | 礼貌的拒绝消息 |

#### System Prompt 核心约束

```
你是饮食记录助手。你只能做三件事：
1. 帮用户记录饮食（需要解析食物→展示确认卡片→用户确认后保存）
2. 回答与食物/营养相关的问题
3. 拒绝与饮食无关的请求

记录饮食时必须先展示确认卡片，用户确认后再保存。不要跳过确认步骤。
估算热量时，如果数据库没有精确匹配，用你的知识合理估算并标注"约"。
```

#### Agent 状态定义（LangGraph State）

```python
class AgentState(TypedDict):
    messages: list[BaseMessage]      # 对话历史
    user_id: int                     # 当前用户 ID
```

### RAG 食物知识库

#### 数据来源

1. **中国食物成分表**（官方出版物数据）
2. **USDA FoodData Central**（英文补充）
3. **常见中式菜品数据**（人工整理/社区贡献）

#### 向量化流程

```
原始食物数据 → 结构化清洗 → 生成文本描述 → Embedding → PGVector
                              │
                              │ "食物：红烧肉。每100g含热量约245kcal，
                              │  蛋白质15.3g，碳水化合物5.2g，脂肪19.8g。
                              │  常见于中式热菜，以五花肉为主料。"
```

#### 检索策略

1. 用户输入食物名称 → `search_food` 工具调用
2. PGVector 检索 top-k 相似食物
3. 返回结果 + 相似度分数
4. Agent 判断：分数 > 阈值直接使用，分数低则 LLM 估算并标注

#### 数据更新

- 初始导入：离线脚本批量处理
- LLM 估算的新食物自动写回向量库（人工审核标记）
- 后续可做用户自定义食物

## 数据模型

### TiDB Cloud 表结构（MySQL 兼容）

```sql
-- 用户表（极简，纯对话无头像昵称需求）
CREATE TABLE users (
    id          BIGINT AUTO_INCREMENT PRIMARY KEY,
    openid      VARCHAR(64) UNIQUE NOT NULL,
    created_at  TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- 饮食记录表
CREATE TABLE food_records (
    id          BIGINT AUTO_INCREMENT PRIMARY KEY,
    user_id     BIGINT NOT NULL,
    record_date DATE NOT NULL,
    meal_type   VARCHAR(16),          -- breakfast/lunch/dinner/snack
    created_at  TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    INDEX idx_user_date (user_id, record_date)
);

-- 单个食物项
CREATE TABLE food_items (
    id              BIGINT AUTO_INCREMENT PRIMARY KEY,
    record_id       BIGINT NOT NULL,
    food_name       VARCHAR(256) NOT NULL,
    amount          DECIMAL(10,2),    -- 重量(g)
    unit            VARCHAR(32),
    kcal            INTEGER NOT NULL,
    protein_g       DECIMAL(8,2),
    carbs_g         DECIMAL(8,2),
    fat_g           DECIMAL(8,2),
    source          VARCHAR(16) DEFAULT 'db',  -- db / llm_estimate
    INDEX idx_record (record_id)
);
```

## 错误处理

| 场景 | 处理 |
|------|------|
| 语音识别失败 | 提示用户重试，自动切换到文字输入 |
| LLM 超时/不可用 | 返回"正在思考中，请稍后再试"，前端显示加载态 |
| 食物解析置信度过低 | Agent 在卡片中标注"热量为估算值"，提示用户可手动修改 |
| 微信登录失败 | 提示重新授权 |
| JWT 过期 | 返回 401，小程序自动重新 wx.login |

## 用户裂变（第二期）

### 分享卡片

**核心载体**：生成精美「每日饮食总结」图片，用户可分享到微信群/朋友圈。

**内容构成**：
- 热量环 + 三大营养素
- 当日食物清单
- Agent 一句话点评
- 小程序码（扫码进入饮食助手）

**入口设计（A + C 组合）**：
- Agent 主动触发：里程碑时刻（连续记录 3 天、累计 100 餐等）提示生成卡片
- 确认卡片底部：保存成功后出现小分享 icon，不抢眼但可见

**技术方案**：
- 小程序端 Canvas 渲染卡片图片，不增加服务端压力
- 调用 `wx.shareFileMessage` / `wx.showShareImageMenu` 分享

### 好友组队/监督

- 双方扫码确认绑定，饮食记录互见（只读）
- 监督模式——对象/朋友之间互相看热量，增强留存

### 邀请奖励

- 有效邀请（完成首次记录）赠送 LLM 调用额度
- 通过 `wx.shareAppMessage` + 邀请参数追踪

### 隐私设计

- 所有分享必须用户主动触发，无默认公开
- 组队绑定需双方确认，不可单向添加
- 用户可随时解绑

## 非功能需求

- **对话延迟**：Agent 采用 SSE 流式返回，首字延迟 < 3 秒
- **数据隔离**：所有查询带 `user_id` 过滤
- **可扩展性**：RAG 数据库与 Agent 解耦，后续可替换 LLM/Embedding 模型
